## Tool schemas and the MCP protocol

- **Anthropic API requires JSON Schema draft 2020-12** for tool input schemas. Since zod 4 the schemas are emitted by zod's own `z.toJSONSchema` with `target: "draft-2020-12"`, `io: "input"` and `reused: "inline"`; `toDraft2020()` stays as a defensive pass. Under zod 3 the converter was `zod-to-json-schema`, which has no 2020-12 target — `openApi3` emits `nullable` (rejected) and `jsonSchema7` emits the draft-07 tuple form `items:[...]` (rejected; 2020-12 wants `prefixItems`). Do not go back to it.

  **Three things the zod 4 emitter does differently, each corrected or accepted on purpose** (measured against the zod 3 output when the dependency moved to 4.6, Dependabot GHSA-mrhx-c7xc-m3w5). A non-`.strict()` object is emitted open in `io: "input"`; the `override` in `toolInputSchema()` closes it again, because zod strips the extra key the model would have been invited to send. `.int()` carries the ±2^53 safe-integer range; the override drops it as noise paid for in every `tools/list`. A `discriminatedUnion` emits `oneOf` rather than `anyOf`, which is equivalent when the branches are disjoint by literal, and is kept.

  **`.default(x).optional()` is not decorative in zod 4.** Under zod 3 the outer `.optional()` let `undefined` through and the default only ever reached the JSON Schema; zod 4 applies it, so every such field would arrive at the panel as an explicit value. The schemas use `.optional().meta({ default: x })` instead — the default shown to the model, absent left absent. A bare `.default(x)` (no `.optional()`) applies in both versions and is unchanged. `tests/unit/run-jsx-args.mjs` ("the resolver invents nothing") is the test that caught it.

  **What the rejection is, exactly.** Both known rejections are *invalid draft
  2020-12*, not "valid but unsupported": `nullable` is an OpenAPI extension and
  the draft-07 tuple form means something else in 2020-12. There is no keyword
  whitelist to stay inside — the emitted document has to be a valid schema in
  that dialect, and composition keywords are fine. This server already ships 16
  `anyOf` sites and 56 `prefixItems`. **Validate, do not guess:**
  `tests/unit/schema-constraints.mjs` checks all 89 emitted schemas against the
  real 2020-12 metaschema and compiles each one with `ajv/dist/2020`, and CI
  runs it. A schema the API refuses takes down *every* tool in the session, not
  the one it belongs to, so nothing goes into that emission pass unvalidated.

  **`$schema` used to be a lie, and the lie was load-bearing in the wrong
  direction.** zod-to-json-schema (the zod 3 converter) stamped `http://json-schema.org/draft-07/schema#`,
  and `toDraft2020` then writes `prefixItems` — which does not exist in draft-07
  — and `items: false`, which there means "no array items at all". Anything
  honouring the declared dialect would have rejected every colour and every 2D
  point in this API; it worked only because tool schemas are read as 2020-12
  whatever they claim. `toDraft2020` now rewrites `$schema` to
  `https://json-schema.org/draft/2020-12/schema` (`JSON_SCHEMA_DIALECT`). That
  also lets the test validate **exactly what ships** rather than a copy with
  the header stripped — ajv refuses to compile a document declaring a dialect
  it was not built for, so before this the test would have had to mutate its
  own subject.

  **The converter silently drops `.refine()` / `.superRefine()`** — `zod-to-json-schema` did, and `z.toJSONSchema` does too. Not an
  error, not a warning — the constraint is enforced on the server and absent
  from the document the model reads, so the only way an agent learns the rule
  is by having a call rejected. See "Cross-field rules" in [architecture.md](architecture.md); `toolInputSchema()`
  in `server.ts` is where declared rules are put back.
- **A `notifications/progress` sent after its request's response reaches nobody, and until 0.5.0 that was every one of them.** The MCP client registers a progress handler when a request carrying a `progressToken` goes out and deletes it the moment that request's response arrives — a notification for the token after that is dropped, and the SDK client logs it as a progress notification for an unknown token. A chunked `run_batch` answers with its `{jobId}` envelope *before the first chunk runs*; that is the whole point of the async path, and it means the request whose token the server was binding had already been answered before the panel reported anything. Every progress message went out on a token nobody held (issue #82). It was verified by reading the raw stdio stream, where the messages are plainly present, and never through a client that correlates them — the same shape of mistake as the undo groups in #69: the wire, like `endUndoGroup()`'s return value, looks identical either way. Two things follow. **Progress belongs to the call that blocks for the job**, which is `await_job`: it binds an emitter to its own token for exactly the span of its own call, and `forwardJobProgress` in `server.ts` unbinds and then awaits every send already started *before the handler returns*, so on the wire every notification precedes the response — on the timeout path as well, where the emitter would otherwise outlive the call and go on sending after the error response. It sends through the SDK's request-scoped `extra.sendNotification` rather than `server.notification`, because that is what ties a notification to a request: it carries the request id (a Streamable HTTP transport delivers it on that request's own stream) and drops anything sent after the request is cancelled. And **nothing may bind an emitter to `run_batch`'s token again**, however natural it looks beside `jobs.register` — that is the bug, exactly. `tests/unit/job-progress.mjs` drives the real SDK client with `onprogress` and records both sides of the wire, and it fails against the 0.4.0 `server.ts`; a test that only counts notifications sent would pass against it, which is what the old one did.
- **A scoped read must say what it left out.** `include`, `maxKeyframes` and `shapeDepth` on the read ops exist because a tool result is re-sent on every later request — a 65k-token `get_layer_full` is paid for once per call and then again on every request until the session ends. Two rules keep them honest: absent means *everything*, so no existing caller changes behaviour; and anything dropped is named and counted in the response (`included`, `keyframesOmitted` + `keyframesTruncated`, `childrenOmitted`), because a short answer that looks complete is the same class of lie as a swallowed error. Note what the call sites depend on: `(args && args.include) ? args.include : null` works because an empty array is truthy in JS, which is exactly what makes `include: []` mean "core fields only". Adding a `.length` guard there would quietly turn it back into "everything". **`find_layers` is the one read where absent means the core, not everything, and that is deliberate** (issue #87): it is a search, so the reason to call it is to learn which layers exist and what to address them by, and the full `__layerSummary` on every match cost ~2k tokens for nine name hits. Its default is `[]` rather than `null`, the section names are `list_layers`' own through the same function — `LAYER_SUMMARY_SECTIONS` in `schemas.ts` is the single list both schemas read, so they cannot drift — and the result is `{matches, count, compsSearched, included}` so the bounded answer still says so. `includeParam()` is not reused there because its sentence says "omit for all of them". `tests/unit/find-layers.mjs` holds the default, the echo, and that the filters cannot be hidden by the section list. Do not "fix" it back to `null` for consistency; the description promises the bounded form. **Effect parameters are the second exception** (issue #115): `list_effects`, `get_layer_full`'s `effects` section and `add_effect`'s return all serialize at most `EFFECT_PARAMS_DEFAULT` (200) parameters per effect when `maxParams` is absent. Every built-in effect has under 15 and the heavy common third-party ones under 100, but Trapcode Particular exposes 7,401 flat parameters — one `list_effects` on it was 1 MB, ~265k tokens — and on a client with no oversized-result guard one call ends the session. The size of an effect is invisible from its name, so no agent could know to pass a cap first; that is what makes "absent means everything" the wrong default here. The cap stays honest the usual way: every effect carries `paramCount`, a capped one adds `paramsOmitted` and a `paramsTruncated` sentence naming `maxParams` and `paramFilter` (a case-insensitive regex over name/matchName, counted in `paramsMatched`). The number lives twice — `EFFECT_PARAMS_DEFAULT` in `schemas.ts` for the description, `__EFFECT_PARAMS_DEFAULT` in `effects.jsx` for the panel — and `tests/unit/effect-params.mjs` fails if they disagree. `add_effect` takes no knob; it is a write, and the agent reads more with `list_effects`.

- **A tool switched off must be switched off at every door, and there are three.** `tools/list` (not listed), `tools/call` (refused before anything reaches the bridge) and `run_batch` (a step naming it refuses the whole batch). The third is the one that is easy to miss: `batch.jsx` calls `OPS[step.op]` directly, so a `run_jsx` step inside `run_batch` runs the script with `run_jsx` nowhere in the tool list — and so does one inside a `run_batch` *nested* in it, which got past the first version of the check because it read only the outer list. The walk is recursive, bounded at `MAX_BATCH_DEPTH`, and refuses a nested `ops` it cannot read as an array. A new route that reaches `OPS` by name — anything that forwards an op name chosen by the model — has to ask `disabledOps()` too. The read-only decision for each `"server"` op is a typed table (`READ_ONLY_SERVER_OPS`), so adding a server op fails the build until it is decided. See "Tool switches" in [architecture.md](architecture.md); `tests/unit/tool-policy.mjs` holds all three doors.
- **A key that is harmless in JSON can be a prototype in ExtendScript.** Every check this server makes reads own keys of an object `JSON.parse` built, where `"__proto__"` is just a key; the panel's ExtendScript parses the same text again and may treat it as the prototype, making a value visible there that was invisible here. `findUnsafeArgKeys` refuses `__proto__`, `constructor` and `prototype` anywhere in any op's raw args before anything else runs. A test fixture for this must be built with `JSON.parse`. Written as an object literal in the test, `__proto__` sets the fixture's own prototype and the key never reaches the wire, so the test passes against code with no check at all.
- **`${user_config.…}` reaching the server unexpanded must read as off.** The switches fail closed on an unrecognised value, which is right for a typo and wrong for a placeholder: a client that ever stopped substituting would turn every Claude Desktop install read-only. `parseSwitch` special-cases `${user_config.<key>}` and nothing broader — any other `${…}` is a person's value and fails closed — and the test pins both.

## The issue journal

- **A directory's mtime does not move when a file inside it is rewritten in place.** The failure cache in `issues/failures.ts` was specified as "keyed by directory mtime", and that key would have missed every write this module makes: `mark_issue_reported`, `archive_issue` and a re-log all rewrite an existing file, which changes the file's mtime and size and leaves the directory entry — and therefore the directory's mtime — untouched. A directory-keyed cache would have served the pre-write entry for the rest of the session while `list_known_issues`, which reads fresh, disagreed. `JournalCache` keys per file on size + mtime, drops files that have gone, and refreshes its own writes explicitly for filesystems whose mtime resolution is coarse enough to hide a rewrite of the same size. `tests/unit/issue-journal.mjs` counts parses across an in-place `markReported`.
- **"No version" is not "an older version".** Every journal file written before 0.5.0 has no `lastVersion`. Reading that as older than the running server would have archived the entire existing journal the day the stamp shipped — the same mistake `export_mogrt` avoids by refusing only on an explicit `0` controller count, pointed the other way. `compareVersions` returns `null` for anything it cannot parse and `archiveReason` treats `null` as live; such an entry leaves by age, or gets stamped by its next sighting and then follows the version rule like any other.
- **The failure path must never fail twice, and must not match itself.** `annotateFailure` wraps the whole lookup: a journal it cannot read, a file it cannot parse, a stamp it cannot write — each logs to stderr and the original message goes back byte-identical. And because an agent pastes the *whole* tool error into `errorText`, pointer block included, `normalizeErrorText` cuts everything from `Known from earlier sessions:` onward before comparing; without that, every entry logged from an annotated failure would carry the previous pointer's text and match on it, and the journal would start answering failures with entries about other entries.
- **The matcher's minimum length is load-bearing in both directions.** A normalised text under 20 letters is never trusted as a prefix (`AE: It broke.` must not match everything about a tool), and the 60-letter prefix rule exists so that two long messages differing only in a tail match — while every `Invalid arguments for <tool>` rejection, which shares its first 30-odd letters with every other rejection for that tool, does not. Both are asserted; a fixture that is too short to match is the test's fault, not the matcher's, and the test says so where it happened.


## Tests and CI

- **`process.exit()` straight after a `fetch` crashes Node 24 on Windows.** A libuv assertion (`!(handle->flags & UV_HANDLE_CLOSING)`, `src\win\async.c`) fires at exit, after every test line has printed and passed — nodejs/node#56645, still reproducing on `windows-latest` under Node 24 as of mid-2026, fixed in Node 26 and never backported. It hit `tests/unit/issue-journal.mjs` twice in a row on the 0.5.0 PR while its three siblings that boot the real server the same way (`write-queue-server`, `job-progress`, `port-drift`) passed — a race, not a difference between the tests. All four now settle for 200ms before exiting, which is the workaround every affected project uses; `issue-journal` also closes the MCP pair and the stub first. The exit stays explicit because the server's WS client reconnects on a timer it owns, so the process would never drain on its own.

## Packaging, binaries and generated files

- **`panelSourceDir()` must prefer the checkout over the vendored copy.** After any `npm pack`, a stale `packages/mcp-server/panel/` is left on disk (gitignored). If that were checked first, `setup_panel` in a dev checkout would install the stale copy instead of what you're editing. Order matters in `setup/paths.ts`.
- **esbuild preserves the entry point's hashbang.** Adding a `banner` with `#!/usr/bin/env node` produces a second one on line 2 and the published binary dies with a syntax error. `prepare-package.mjs` asserts there is exactly one.
- **A compiled binary has no module paths.** `import.meta.url` inside a `bun --compile` build points into the executable's virtual filesystem, so `packageRoot()` finds nothing. `setup/paths.ts` falls back to `executableDir()` — the panel, `package.json` and a real `node_modules/ws` ship *beside* the binary, which is why every binary target is a folder and not a single file. Shipping the bare executable would break `setup_panel` with no obvious cause.
- **`require.resolve` does not throw in a compiled binary — it returns the bare specifier.** `require.resolve("ws")` gives back `"ws"`, not a path and not an exception. Anything that treats a failed resolve as a throw is therefore dead code there, and `path.dirname("ws")` is `"."` — the *working directory*. v0.2.0 copied that into the CEP extension folder, which produced an empty `node_modules/ws` for a server started somewhere empty, and would have attempted to copy the entire filesystem for one started at `/`. `wsModuleDir()` now requires `path.isAbsolute` before believing the resolver and confirms every candidate with `isWsModuleDir()`. **Validate resolver output by its contents, never by `existsSync`.**
- **`ws` can never be inlined.** `setup_panel` copies the directory into the CEP extension, because AE's CEF process cannot resolve modules out of this package. Every packaging path (`prepare-package.mjs`, `build-mcpb.mjs`, `build-binaries.mjs`) has to keep it as a real directory on disk. A signed panel carries a second copy *inside* `panel/node_modules/ws`, because the signature covers it; the copy beside it stays for unsigned builds.
- **The signed panel (issue #182) is a packaging step, never a source state.** `scripts/lib/panel-signing.mjs` — `vendorPanel` is how all three packaging scripts put the panel down. Unset, nothing is signed (a dev `npm pack`, `make artifacts`, ci.yml). `AE_MCP_PANEL_SIGN=required` makes an unsigned result a failed build. **A release signs once, before the tag, and CI never signs.** `release.sh` runs `panel-signing.mjs sign` a single time — with `ws` fetched at the lockfile's version and checked against its integrity hash, never taken from `node_modules` — and exports `AE_MCP_SIGNED_PANEL`; `vendorPanel` then copies that folder verbatim into the npm tarball, the `.mcpb` and every binary — after checking it is intact and is exactly this checkout's panel plus `ws` (`prebuiltMismatch`), so a stale signed folder cannot ship. One certificate, one timestamp, byte-identical `signatures.xml` everywhere. Signing in CI would put Rosetta, a download and a timestamp server after the tag, which the release ordering forbids; so `release.sh` also packs the npm tarball itself, installs and smoke-runs it (`release-checks.mjs smoke-npm`), records its SHA-256 in the annotated tag, and attaches it to a draft GitHub release created before anything is pushed (published after the push); `release.yml` — triggered by the release being published — refuses an asset whose SHA-256 differs from the tag's, then publishes that exact file over OIDC (`--provenance` then names the workflow as publisher, not as builder). **Ephemeral is deliberate:** CEP accepts any self-signed certificate and checks only that the files match, so a persistent certificate buys no trust and is one more secret; `release.sh` defaults `AE_MCP_PANEL_CERT` to `ephemeral`, made with a random password for the one signing and deleted with its work folder. A persistent `.p12` (`AE_MCP_PANEL_CERT` + `AE_MCP_PANEL_CERT_PASSWORD`, environment only, `*.p12` gitignored) still works. ZXPSignCmd accepts the password only on its command line, so it is briefly visible to the same user's processes; it is never echoed, and `runTool` builds failure messages from the tool's output with the password redacted — never from Node's `err.message`, which quotes the whole command line. Signatures are timestamped (`AE_MCP_PANEL_TSA`, DigiCert by default) so they outlive the certificate; the ephemeral certificate is also issued for 100 years.
- **ZXPSignCmd is pinned, checked and Intel-only on macOS.** Downloaded from `Adobe-CEP/CEP-Resources` at a fixed commit (`ZXPSIGNCMD` in panel-signing.mjs: version 4.1.3, both platforms' SHA-256), cached in `node_modules/.cache/zxpsigncmd/`, and re-hashed before every use — a mismatch refuses to run it. The macOS build is x86_64, so an Apple-silicon release machine needs Rosetta; `release.sh` checks for it up front. `AE_MCP_ZXPSIGNCMD` overrides the download. To move versions, change the commit and both digests together.
- **Signing is checked at every hand-off, the last from the archives that get uploaded.** The signing extracts `META-INF/signatures.xml` and `mimetype` from the `.zxp` ZXPSignCmd writes (with the server's zip reader, `frames/mogrtThumbnail.ts`), then runs the repo's digest check (`setup/panelSignature.ts`) and `ZXPSignCmd -verify`. `release-checks.mjs smoke-npm`/`smoke-mcpb`/`smoke-binaries` repeat the verify on the installed tarball and the unpacked archives when `AE_MCP_PANEL_SIGN=required` — npm 11 keeps a nested `node_modules` under `files`, which `smoke-npm` measures rather than assumes.
- **Bare Mach-O binaries cannot be stapled.** `xcrun stapler` only writes tickets into bundle formats (.app/.pkg/.dmg). The release notarizes the *zip* and lets Gatekeeper verify online on first launch. Do not add a `stapler staple` call expecting it to work.
- **`notarytool submit --wait` finishing is not Apple accepting.** It can exit 0 with `"status": "Invalid"`. `sign-and-notarize.sh` asks for `--output-format json` and passes only an exact `Accepted`, via `parseNotaryResult` in `scripts/lib/release-checks.mjs`; anything else prints `notarytool log` and stops before the tag (issue #162). Then `release.sh` unpacks the `.mcpb` and each host-runnable binary zip, re-verifies the signature inside the zip, and requires `tools/list` to match `OpSchemas` exactly (issue #168). The Windows binary cannot run on the Mac that cuts the release and goes out without a smoke run — the script says so rather than skipping it silently.
- **The hardened runtime blocks JIT.** Bun embeds JavaScriptCore, so `scripts/entitlements.plist` must grant `allow-jit` and `allow-unsigned-executable-memory`. Without them the binary signs and verifies fine and then refuses to launch — on someone else's machine, not yours.
- **Generated files under `plugin/` will be overwritten.** `plugin/skills/**` — SKILL.md and `references/*.md` alike — and `plugin/commands/**` come from `src/{guides,prompts}/*.md`. Hand-edits survive until the next `npm run build`. Every generated directory is owned *wholesale*, down to each skill folder, so a renamed or re-parented source cannot leave a second copy behind for an agent to read. CI runs `build-guides.mjs --check` to catch this at review time rather than in a release.
