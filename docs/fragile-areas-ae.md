# Fragile areas — After Effects and ExtendScript

Measured behaviour of After Effects 2026 and its scripting engine, and the
decisions in `packages/jsx/` that follow from it. Everything here was found by
running against a live AE; several entries contradict Adobe's documentation.
**Undo behaviour, frame rendering and the TextDocument round trip are measured
before they are claimed anywhere.**

## ExtendScript, the language and `run_jsx`

- ExtendScript single-threading: `run_jsx` with a long synchronous loop will freeze AE's UI. Document for the agent in the tool description (already done).
- **ExtendScript parses chained ternaries left-associatively.** `a ? x : b ? y : z` evaluates as `((a ? x : b) ? y : z)`, so the first truthy branch becomes the next condition and everything falls through to the last alternative — no throw, just the wrong answer. `get_project_summary` labelled every project item `"folder"` for two releases on one such line (issues #21/#22). Write if/else chains in `packages/jsx/*.jsx`; parentheses parse correctly too, but a later edit can drop them. `tests/unit/jsx-ternary.mjs` scans the sources and fails the build — there is no offline ExtendScript runtime, so nothing else can.
- **`run_jsx` must never answer `null`.** A script whose last statement is a bare expression completes and yields `undefined` — `"ping";` does not return `"ping"` — with every side effect already applied. Answering that with a bare `null` made "ran fine, returned nothing" identical on the wire to "did not run", and the natural response to a suspected failure is to run the script again: nothing rolls back, so a second run of a non-idempotent script duplicates layers, re-applies `moveTo` and writes keyframes on top of keyframes (issue #43). The guidance to prefer few large scripts makes the ones most likely to be re-run the most destructive to re-run. `__rjResult` therefore wraps *any* null — `undefined` and an explicit `return null` alike — in `{ok:true, returned:null, undoGroup, note}`. A returned value still comes back bare, falsy ones included; the envelope is for nothing, not for falsy.

- **`run_jsx`'s error line counts from something the caller cannot see.** The reported number did not map onto the submitted script and the shift was not even constant between calls — the same "line 22" pointed at two different statements in consecutive calls (issue #46). It costs more here than anywhere else: nothing rolls back, so an agent that cannot locate the throw either reads the whole project back or, worse, runs the script again and applies the completed half twice. Two things fix it, and the second is the one that survives being wrong. First, the caller's line 1 is a **counted** distance down the evaluated source: `__RJ_WRAP_PREFIX` carries no newline, and `__rjBuildSource` measures the preamble it actually built rather than asserting a constant — which matters now that `libraries` are inlined into that preamble and its length changes per call. Second, the failure is reported with the line's **text**, which needs no trust in any numbering, and `__rjSourceInfo` refuses to map a line that falls outside the script rather than clamping it — a confident wrong number sends the reader to a statement that did not fail; a line that lands in an inlined library is attributed to that file by name instead. `aeErrorText()` in `util/errors.ts` is the one place this becomes prose. `tests/unit/run-jsx-lines.mjs` holds the preamble invariant, with and without libraries; nothing else can, since there is no ExtendScript to run offline.
- **`Error.start` and `Error.end` are 0 on every ExtendScript error in AE 2026, and 0 is not an offset.** The documentation presents them as character offsets into `Error.source` — a better answer than `Error.line`, because they need no assumption about what `line` counts from. Probed inside AE, catching from a four-line script that throws on its last line: `eval("(function(){ var a=1;\nvar b=2;\nvar c=3;\nnope.boom();\n})()")` → `{ "line": 4, "start": 0, "end": 0, "srcLen": 57 }`. **`line` is already correct.** The offsets came back 0 however far into the source the throw was, so reading them as offsets put *every* failure on line 1, printed line 1's text, and demoted the true number to the parenthetical afterwards — which is how #46 was reported fixed while every error still said line 1. The branch is kept but guarded: `start === 0 && end === 0` means After Effects declined to say, not that the error is at character zero, and only a non-zero start (or a zero start with a non-zero end) is believed. Do not restore it from the documentation. `tests/unit/run-jsx-lines.mjs` carries a stub built from that probe — the old stubs all omitted `start` entirely, which is exactly why they were green.
- **`app.executeCommand()` silently no-ops through the bridge.** `app.executeCommand(2080)` (Edit → Duplicate) runs, throws nothing, and does nothing: menu commands need host/panel focus and an active selection, and CEP's `evalScript` guarantees neither. It fails in the worst available shape — a success result for work that did not happen — and only surfaces later as a missing item. There is nothing to fix in code, so the `run_jsx` description names the failure and points at the API equivalents (`CompItem.duplicate()`, `layer.duplicate()`). Reported as issue #47.
- **`$.evalFile` does not evaluate at global scope — it evaluates into the calling function's scope, exactly as `eval` does.** The whole first design of `run_jsx`'s `libraries` rested on the documented claim that it does: the server sent `{path, hash}`, the panel `$.evalFile`d each file from a loader function, and the promise was "load once, call for the rest of the After Effects session". Probed inside AE 2026, calling `$.evalFile` from the body of an eval'd script on a library declaring `function rig2()` and `var RIGVAR = 3`: `{"exists":true, "typeofRig2_local":"function", "typeofRIGVAR_local":"number", "globalRig2":"undefined", "viaGlobal":null}`, and on the next `run_jsx` call in the same session `{"typeofRig2":"undefined", "viaGlobal":"undefined"}`. Everything a library defined lived inside the loader and was gone before the wrapper ran, so `libraries` answered `Function rig is undefined` every time, for every library, in every session — and the per-session hash cache only ever skipped work whose result had already been discarded. The library source is now **inlined into the same eval as the caller's script**, ahead of it, which is the only arrangement that puts a library's declarations in the script's scope. Three things follow and all three are handled rather than left to surprise someone: the server sends `{path, text}` because the panel now needs the bytes, not a path (context is saved in the *conversation*, which the server-to-panel hop was never part of); a library is re-evaluated on every call, so libraries are for declarations, not for work; and the library text shifts the caller's line 1 down, which is #46's exact failure mode, so `__rjBuildSource` counts the preamble it built and hands it to the mapping. A library is also parse-checked on its own — `eval("(function(){ " + text + "})")`, never called — before it reaches the shared eval, because a missing brace in a library otherwise takes the whole wrapper down at whatever line AE's parser gave up on, frequently a line of the caller's script.
- **The ExtendScript engine is shared with every other script in After Effects, so the bundle publishes one global, `__AEMCP`, and nothing else (issue #185).** Measured on 26.5: the panel's `evalScript` runs in `main`, and so do other CEP extensions' `evalScript`, File > Scripts, ScriptUI panels and osascript's `DoScript`. With the bundle's bare top-level names, a ScriptUI panel's `OPS = {}` failed every op as `Unknown op` (which the server then misread as "panel out of date"), an osascript `function dispatch(){}` failed every op, a File > Scripts `getCompById` made `get_comp` throw the hijacker's error, and a second extension's `ease` silently replaced `run_jsx`'s; in the other direction our `ease`/`shape`/`getCompById` overwrote whatever another script had defined. `#targetengine` is not the fix: it isolated a `DoScriptFile` script, but as the first line of an `evalScript` string AE raised a modal "Syntax error" per call that blocked quitting, and `evalScript` is the only route every op takes (`#targetengine` in the manifest's `ScriptPath` file is unmeasured). So `scripts/bundle-jsx.mjs` wraps the concatenation in **one function**: every declaration in `packages/jsx/*.jsx` is a local of that closure, with no change to how the files are written, and the closure ends by assigning `$.global.__AEMCP = {id, call, dispatch}`. The panel sends `__AEMCP.call(payloadJson)`, which stringifies with the bundle's own `JSON` — `core.jsx` captures the engine's native one at load if it still round-trips, else its polyfill — so a later `JSON = …` cannot break the envelope either. `OPS` and `JOBS` are deliberately not on the namespace: nothing outside can reach them. `run_jsx` keeps every documented helper because its direct `eval` runs inside `OPS.run_jsx`, whose scope chain is the closure — helpers are now closure locals, not globals, which the description never promised otherwise. What another script can still do is replace or delete `__AEMCP` itself; every op is sent guarded by a check that `__AEMCP.id` is ours, answers a sentinel instead of running when it is not, and the panel then re-`$.evalFile`s the bundle once (what `/reload-jsx` does, measured to restore every case above) and re-sends — safe, because the sentinel means nothing ran. The heal goes through the `evalScript` mutex, and it only re-loads the bundle the panel booted with: if the installed `bundle.jsx` hashes differently (the window between `setup_panel` and the next launch) it refuses with "Nothing ran. Restart After Effects", because loading it would mix a new bundle with the running `main.js` and move `bundleHash` onto the installed hash, which would let the version gate call a stale panel current. Three consequences. A reload starts from fresh tables (`OPS`, `JOBS`, every module-level cache) rather than `X || {}` keeping the old ones, so a chunked `run_batch` in flight across a heal or `/reload-jsx` loses its job; `driveJob` turns the resulting bare `No job: j_…` — and every other failure of an in-flight job, including a refused heal, whose "Nothing ran" is true of that call and false of the batch — into one that says how many ops had been attempted (the cursor, so continue-on-error failures are not called applied) in how many undo steps, and not to re-run the batch as it was — a silent restart of it would apply the first chunks twice. Preserving `JOBS` was rejected: the heal runs precisely when `__AEMCP` is gone, so anything kept on it is gone too. And `/reload-jsx` does not reload `main.js`, so moving a panel from a pre-#185 bundle to this one needs an After Effects restart, not a reload. `tests/unit/bundle-namespace.mjs` evaluates the built bundle beside a hostile neighbour in both directions. *Unmeasured live:* that `$.global.__AEMCP` is visible as a bare name to the next `evalScript`, that a direct `eval` inside a nested function sees the closure (the `$.evalFile` probe above shows it sees the calling function's scope), and the self-heal itself.


## Undo groups

- **An undo group does not survive an `evalScript` boundary. Measured, and it costs three releases of a false guarantee.** `app.beginUndoGroup(name)` in one `evalScript` call and `app.endUndoGroup()` in a later one does not produce one undo step — After Effects **discards** the group, and every write inside it lands as its own step with its own AE-generated name. The evidence, gathered against AE 2026 while verifying 0.4.0 (issue #69): a 600-op `run_batch`, which opened its group in `run_batch` and closed it from the last `_continue_job`, produced **~600 undo steps**; one Cmd-Z took the comp from 601 layers to 600 and the Edit menu read `Undo New Solid`, not the batch's group name. A controlled probe — begin in one call, write in a second, end in a third — reproduced it on its own. Nothing raises, nothing warns, and the return value of `endUndoGroup()` is the same either way, so the only way to see this is AE's Edit menu.

  Two consequences are permanent. **Every group must open and close inside one call**, which is why `run_batch` is one group inline and one group per chunk when chunked, and why `core.jsx` funnels every `beginUndoGroup` through `__beginUndoGroup` and counts them — the `undoSteps` a batch reports is the counted delta, so the number an agent repeats to a user as "press Cmd-Z N times" is measured rather than intended. And **a design that needs a group to span calls cannot have one**: `singleUndo:true` buys the single step back only by giving up the chunking entirely, blocking AE for the whole batch, which is a real cost and is stated in the tool description rather than hidden.

  This is the third bug in this release traced to Adobe's documentation asserting something AE does not do — `CompItem.posterTime` and `exportAsMotionGraphicsTemplate`'s surviving object references are the other two. **Undo behaviour, like `saveFrameToPng`, is measured against a live AE before it is claimed anywhere.** `tests/unit/batch-undo.mjs` cannot see AE's undo stack, so it asserts the property that decides it: no dispatch call ever returns with a group still open.

- **`run_jsx`'s undo group collides with `copyToComp`.** AE refuses to copy a layer that has a parent or a linked expression while an undo group is open, so `dispatch()`'s wrapper broke exactly the rigs worth copying (issue #30). `run_jsx` now takes `undoGroup:false`, resolved per call through the predicate form of `__meta.noUndo`, and `core.jsx` exposes `withoutUndoGroup(fn)` for closing the group around one statement. Keep the opt-out on the handler's `__meta` — dispatch must stay stateless between calls, or one op's opt-out leaks into the next.

- **A screenshot borrows project state, and every borrowed assignment is an undo step.** `saveFrameToPng` renders at `comp.resolutionFactor`, so `__saveFrameAt` sets the factor it was asked for and restores the user's (issue #72), and `screenshot_layer` flips solo switches the same way. After Effects records each assignment, restore included, as its own anonymous step — "Resolution change" — so one frame plus a four-tile sheet left ten no-op steps on top of the agent's last real edit, measured on 25.1 (issue #116). Two things fix it, both in `vision.jsx`. The assignment is **skipped when the comp is already at the requested factor**, which keeps #72's guarantee (the render still happens at the factor named) and makes a comp already at the requested factor — Full shot at `downsample: 1`, say — cost nothing. That is not the default: with `downsample` omitted, a 1080p comp at Full resolves to 2 and still takes the group. Otherwise **the borrow and the restore share one group, `AE MCP: screenshot`**, opened through `withUndo` inside the same call: one step per call, contact sheets included — though a frame or tile the panel retries is a new call and adds one more — recognisable by name in Edit > History. `screenshot_layer` also assigns only the solo switches that are actually wrong. The ops stay `noUndo` at the dispatcher because whether a group is needed depends on the comp's state, and they open none of their own when `__UNDO_OPEN` says one of ours is already open — a screenshot inside `run_batch` joins the batch's step, since AE's groups do not nest. Whether `saveFrameToPng` behaves identically inside an open undo group is **not yet measured**; check it, and the Edit menu, on the next live pass. Rendering at the current factor and resampling in the panel would cost zero steps always, and is the route if a group ever turns out to disturb the render. `tests/unit/screenshot-resolution.mjs` and `tests/unit/jsx-undo-group.mjs` hold the counts.

## Keyframes, easing and expressions

- **`setTemporalEaseAtKey`'s array length belongs to the property, and cannot be read off the value.** Spatial properties (Position, Anchor Point) take a single entry regardless of 2D/3D, because the ease runs along the motion path. Everything else has to be measured, because the count and the value's own length disagree in *both* directions — and the two properties that prove it were documented the other way round for a release, each reading individually plausible, until a live pass measured them. **The measured arities are the `extendscript-gotchas` guide topic's to state, not this file's**: keeping a second copy here is how the resident copy went stale while the guide's stayed right. What belongs here is why the code trusts no table at all — `__applyTemporalEase` derives a count and then still walks a 1-2-3-4 ladder on failure: the derivation is the fast path, not the authority, and the arity it settles on comes back as `easeDimensions` so a caller learns the real answer instead of the documented one. Issue #96 adds a single unreproduced observation — a 2D layer's Position accepting only 3 through raw `setTemporalEaseAtKey` on 26.3 — which is one more reason the ladder, not the table, is the authority. The table has exactly one home, `packages/mcp-server/src/guides/extendscript-gotchas.md`; `animation.md` points at it and must not restate it, and neither may this entry.
- **Assigning `Property.expression` succeeds whatever the text says; `Property.expressionError` is where AE reports that it does not run.** A syntax error or a bad reference throws nothing on the assignment — the failure is a warning banner in the AE UI that an agent cannot see, and until 0.5.0 `set_expression` returned `{ok:true}` for it and `get_expression` never read the field (issue #97). The skill recommends expressions over dense keyframes for anything procedural, so this was the gap between the advice and what could be verified. `__expressionError` in `expressions.jsx` reads the field after **forcing one evaluation** by reading `prop.value` inside a try: Adobe's documentation implies the field is populated when the expression is evaluated, and whether 26.3 fills it in on a bare assignment is not something an offline test can settle, so the nudge makes the answer independent of the question (a group throws on `.value`, which is not an expression error, and an AE without the field reads as no error — both handled). `set_expression` and `toggle_expression({enabled:true})` throw with the path, AE's own message and both ways forward, and say the expression *stays written*: nothing here rolls back, and a caller fixing a typo wants the property it aimed at, not a cleared one. `get_expression` carries `expressionError` alongside `expression` and `enabled`. `tests/unit/expression-error.mjs` has a mock that hides the error until `.value` is read, so a guard that only reads the field fails there. Measured on 26.3x87 (recipe 39, 2026-09-08): the field is populated on assignment, before `.value` is read — the nudge is belt-and-braces there, kept because it costs one read and covers the documented case.
- **Removing the last Time Remap key hides the property.** `while (tr.numKeys) tr.removeKey(1)` on a remap-enabled layer leaves `setValueAtTime` throwing `the property or a parent property is hidden` (issue #86). Setting `timeRemapEnabled = true` already creates the two keys a loop needs, so anything in this repo that builds a loop — a bed in `audio.jsx`, say — edits those keys in place and never clears them; toggling `timeRemapEnabled` off and on restores the defaults.

## Shapes

- **Shape `Contents` renders index 1 in front, and `addProperty` appends to the end.** So the *first* node added is the one on top, which is the opposite of the layer stack, and building back-to-front (body, then title bar, then dots) produces a silent solid slab with no error. The fix an agent reaches for is worse than the bug: `property.moveTo()` looks correct when the comp is rendered standalone and leaves it serving a stale buffer in every **nested** render. `add_shape_content` therefore takes `zOrder` rather than an index — `"back"` is the append AE already does and touches nothing, and `"front"` is the single `moveTo(1)` call site in the codebase, done on the empty node before any property is set so a failure costs an empty node. The guidance everywhere (tool description, guide) is to order the calls front-to-back and never need it. Reported as issue #32; if `moveTo` is ever proven safe, the note in the description comes out, not the option.
- **`moveTo` is a `PropertyBase` method, and a `Layer` is not a `PropertyBase`.** It re-ranks a property inside an indexed group; called on a layer it throws `parent is not an INDEXED_GROUP`, which is what every `reorder_layer` call did from the day the op shipped until 0.4.0 (issue #70). Nothing caught it because nothing offline ran the op, and the error names a concept — an indexed group — that has no counterpart in what the caller asked for, so an agent hitting it at the moment it is trying to fix a layer stack has nowhere to go. Layers reorder with `moveBefore` / `moveAfter` / `moveToBeginning` / `moveToEnd` — the first two take a **layer**, the last two take nothing at all, and none of the four takes an index. The one legitimate `moveTo` in this codebase is the shape-property `moveTo(1)` in the bullet above; `tests/unit/reorder-layer.mjs` gives its mock layer a `moveTo` that throws AE's own message, so a rewrite that reaches for it again fails there rather than in someone's project. Related: because reorder is the op that invalidates every index below it, `reorder_layer` takes `beforeLayerId` / `afterLayerId` as well as `toIndex`, and `toIndex` is documented as the index the layer **lands on** — moving up and moving down need different primitives and the two readings differ by one, silently.
- **A shape node reference goes stale when a sibling is added.** Hold a Fill, add a Stroke to the same group, and the Fill reference starts throwing `Object is invalid`. Add every node first, then re-fetch by name before setting values or expressions. `add_shape_content` re-fetches from the parent after its own `moveTo` for exactly this reason. Reported in issue #24.
- **A new shape layer's origin is now `[0,0]`, not AE's comp centre — and that is a deliberate behaviour change.** `addShape()` leaves Position at the comp centre with the Anchor Point at `[0,0]`, so layer space is offset from comp space by half a frame. Every path this toolset can write — `set_shape_path` vertices, `add_shape_content` vertices, a rect or ellipse `position` — is in *layer* space, while every other coordinate an agent handles (comp size, `sourceRect`, other layers' positions, a screenshot) is comp space, and nothing in the old response said which one it had been given. So a drawing authored in comp pixels came out shifted by `(width/2, height/2)`, and the check that would catch it is a downsampled screenshot: issue #51 cost a review round. `create_shape_layer` therefore takes `position`, defaulting to `[0,0]`, which makes the two spaces the same space; `"center"` is AE's own spawn point kept to one word, and the result echoes the position and anchor point it ended up with so nobody has to render a frame to learn the coordinate system. **What this breaks:** a caller that relied on the old spawn point to centre a motif — `create_shape_layer` then `add_shape_content({type:"rect", size:[200,100]})` with no explicit position — now gets that rect at the top-left corner instead of the middle. The fix is one argument (`position:"center"`), the failure is visible in the first frame rendered rather than three edits later, and the precedent is the `anchorAlign` change in 0.2.1: this repo changes a creation-time default when the old one was wrong in a way that only shows up downstream. `tests/unit/shape-spawn.mjs` holds the default, the escape hatch and the echo.
- **`setValue` can throw for a write that landed, in a comp no viewer is showing.** Reported against 26.3 (issue #129): `setValue([500,190])` on a plain rect's `ADBE Vector Rect Size` — no keys, no expression — threw `invalid numeric result (divide by zero?)` for every rect after the first in a comp that was not open in any viewer, whose `comp.time` read negative (it was nested later down a parent's timeline); every value was in place when read back, `comp.time = …` did not help, and the same writes in a viewed comp never threw. The cost in this repo was the mirror of "never report success for work that didn't happen": `add_shape_content` counted the key as failed, **removed the node it had just built** and said nothing changed, so the agent retried into the same throw. Every first-class `setValue` now goes through `__setValue` in `values.jsx`: on *that* message only, it reads the property back (pre-expression, via `valueAtTime(0, true)`, when an expression is on it) and drops the throw only when the read-back equals what was written — numbers and numeric arrays within a relative 1e-4, a 2D Position's added zero third component and an RGB colour's added alpha of 1 allowed, Shapes compared vertex by vertex with tangents that were never set (a fresh `Shape` holds `[]`, AE reads back `[0,0]` per vertex — measured on 26.5) counted as zero; any other value type, any other error, or a read-back that disagrees rethrows the original error untouched, so this cannot turn a real failure into a success. `run_jsx` scripts get the same function as `setValueChecked`. What it deliberately does not do is the reporter's other workaround, `comp.openInViewer()`: that changes which comp the user is looking at, from a call that never asked to. `setValueAtTime` is left alone — the report is about `setValue`, and a key's read-back is a different comparison; extend it there only once a keyed write is seen doing the same. **Not reproduced on 26.5 (2026-10-29)**: a nested throwaway comp reading `time -2.27`, four groups of rect + fill each, the same writes through raw `setValue` and through `OPS.add_shape_content`, with and without a scale-from-0 rig parent, `sourceRectAtTime` anchor expressions and per-layer Scale keys — no throw. The trigger is narrower than "not in a viewer", or 26.5 fixed it; the guard is cheap and stays either way. `tests/unit/set-value-readback.mjs` holds the contract against a mock that throws AE's message.
- **AE hangs a 48-property `ADBE Vector Materials Group` off every vector group, and it is inert on a 2D shape layer.** It is the 3D extrusion model — Front/Bevel/Side/Back × twelve attributes — and it only means anything for an extruded shape under the Cinema 4D renderer. It was around 75% of the bytes of a shape read: one 68×68 circle in one group cost 4,400 tokens, of which the geometry was about 40 (issue #42). `explore.jsx` skips it unless `shapeMaterials` asks, which is the one place `include`-absent-means-everything does not hold — hence `materialsOmitted` and a note in the response, and hence a separate flag rather than a member of `include`, whose contract would otherwise have to bend. The group Transform beside it is elided by the same walk when every property is still at its creation value, tested against `__VECTOR_TRANSFORM_DEFAULTS` rather than through `PropertyBase.isModified`: the values can be asserted with no AE to run in, and a property that table has never heard of has to fail the test rather than be folded away unread.


## Text

- **Text alignment is justification, never a computed anchor.** `addText()` centre-justifies point text with the anchor at the origin, so the visible left edge sits at `-width/2`. Until 0.2.1 `create_text_layer` implemented `anchorAlign` by measuring `sourceRectAtTime()` and writing that offset into the Anchor Point. It renders identically at creation and is wrong from the first edit onward: the offset is baked for the string that existed then, so retyping, an expression on Source Text, or an Essential Graphics edit in Premiere re-centres the text on a stale anchor and the layout jumps — and any `sourceRectAtTime()` expression sizing a background behind it inherits the error. `anchorAlign` now sets `ParagraphJustification.LEFT/CENTER/RIGHT_JUSTIFY` (the map lives once, in `text.jsx`) and leaves the anchor at `[0,0,0]`, which is live for whatever the layer says later. Reported as issue #24. `"none"` still means "touch nothing".
- **`addText()` inherits the user's Character panel.** Tracking especially: a layer created with no styling arrives at whatever that workspace was last left on — the report that opened #24 measured `-20` — so the same call renders differently on two machines. Nothing in this repo ever set it. `create_text_layer` now writes tracking explicitly (`args.tracking`, or 0), which is the only way to make the tool reproducible; `anchorAlign: "none"` opts out along with everything else.
- **The TextDocument round trip can lose the justification, and nothing says so.** Two reports against AE 26.3, and the mechanism of neither is known. `set_text({text})` on a layer that read LEFT_JUSTIFY (7413) came back CENTER (7415) — the handler reads `src.value`, changes `.text` and writes the same document back, so it is the round trip itself, not a fresh document, that drops it (issue #93). And a script assigning `CENTER_JUSTIFY` through the TextDocument stored RIGHT (7414) while `set_text({justification:"center"})` on its own landed correctly (issue #94). Neither raises, and a layer that silently re-centres is found half a frame off in a screenshot several edits later. The guard that can be built blind is the one this repo asks for anyway: **`__verifyJustification` in `text.jsx` reads the property back after every round trip** and compares it with what should be there — the requested value, or the one read before the mutation — writes the justification alone once more if it moved, and throws naming expected and actual if it still disagrees. `set_text` and `create_text_layer` both go through it (the create path removes the layer it made before throwing, so a failure never leaves a layer the caller has no id for), and both return `justification` by name plus `justificationReasserted`, which is the only way a live run can show whether the reset actually happens. `tests/unit/text-justification.mjs` models both reports as pluggable misbehaviours on a mock Source Text; which of them AE 26.3 actually is, recipe 38 measures — and on 26.3x87 (2026-09-08) *neither reproduced*: `set_text({text})` on a LEFT layer read LEFT back with `justificationReasserted: false`, and `create_text_layer` with `anchorAlign: "center"` and a non-default font landed `center` first time. Both reports were against 26.3, so the guard stays. If the reassert is measured to land reliably, keep it — one extra `setValue` is cheap and the read-back is the contract; if it is measured *never* to land, the mechanism is worth finding before anything else is changed.
- **`TextDocument.justification` written from a script stores the wrong value.** On 26.3, `d.justification = ParagraphJustification.CENTER_JUSTIFY; prop.setValue(d)` lands as RIGHT (`7414`) on a layer made with `addText()`, while the enum reads correctly in that scope; LEFT only appears to work because it is `addText()`'s default (issue #94). `text.jsx`'s own justification map lands correctly, so the tool path is unaffected and the raw path is documented in `extendscript-gotchas.md` under Text, with the `sourceRect.left ≈ -width/2` check. If `set_text` ever starts landing RIGHT for `center`, this is where to look first.

## Audio

- **`layer.property("ADBE Audio Levels")` returns null on an audio layer.** Audio Levels sits inside the layer's `Audio` group, not on the layer, and the only reliable handle is the `layer.audioLevels` shortcut (issue #48). A null there does not throw — it just means the level is never set, on every layer, silently — which is most of the reason `place_audio_cues` exists rather than being left to a `run_jsx` loop. `audio.jsx` uses the shortcut and falls back to the group walk; if neither answers it says so instead of leaving a layer at whatever level the file happened to have. AE's Audio Levels is itself in decibels, two channels, and the tool writes `0` explicitly when the caller gives no level for the same reason `create_text_layer` writes tracking explicitly.
- **A batch op has to be all-or-nothing, because a partial one cannot be described.** `place_audio_cues` can be handed 90 cues; a run that dies on cue 30 leaves 29 sound effects in the timeline and an error naming none of them, and the natural next move — call it again — doubles the first 29. So it plans the whole list with no side effects (resolving every `footageId`, checking every path exists, checking each resolved item has audio, checking every time is inside the comp), reports *all* the offending cue indices at once, and creates nothing if any of them failed. What planning cannot foresee — an import that turns out to be silent, an AE refusal on some particular layer — is caught by a rollback that removes every layer and every import the call made, newest first, layers before items. **The layer joins the rollback list the instant `layers.add()` returns, not once it is configured**; registering it after the last `setValue` leaves exactly the failing layer behind, which the offline test caught before this ever ran in AE. `dryRun:true` is the same planner with the creation phase skipped, and it is not an undo step either — a plan appearing in the user's undo history would make "this changed nothing" false in the one place they can see it.
- **Each of `place_audio_cues`' per-cue options moves something After Effects then quietly resets, so the statement order in `__placeAudioCue` is load-bearing.** `layer.stretch` moves the layer's start time (reported in #85; with the re-assertion in place a stretched cue lands with `startTime` and `inPoint` both at the cue time — measured 2026-09-08: `{time: 5, stretch: 200}` on a 0.3s file → startTime 5, inPoint 5, outPoint 5.6 — while which point AE holds *without* it was not isolated; the mock in `tests/unit/audio-cues.mjs` moves it so a version that forgets the re-assertion fails), so `startTime` is set after it and the trims after that. `timeRemapEnabled = true` resets the out point to the file's own end, so a looped cue's end — the caller's `outPoint`, or the comp's — is re-asserted after remap is enabled, and set *before* the in point: an in point past the file's natural end can only land once the layer is allowed to extend, which is also why the out point goes first on an unlooped cue. **The two Time Remap keyframes AE creates on enabling stay exactly where they are.** Removing every key hides the property, and the next `setValueAtTime` on it throws (issue #86); the loop expression overrides them anyway, so there is nothing to gain. Fade keyframes go last, at the in/out the layer *actually* has, on `layer.audioLevels` — the #48 handle — and Time Remap is reached through `layer.timeRemap` for the same reason, since `layer.property("ADBE Time Remap")` is null on an audio layer even after enabling. `canSetTimeRemapEnabled === false` refuses by name; an undefined does not, on the `hasAudio` principle.
- **The loop expression is the `%` pattern issue #85 measured, with two deliberate substitutions, and one constant that can go stale.** `(time - startTime) % thisLayer.source.duration`: `startTime` in place of the issue's `inPoint`, so a trimmed in point hides the front of the file the way a trim does on every other layer instead of delaying the loop's first cycle; and the duration read live off the layer rather than baked, so a relinked file keeps looping. An expression cannot read a layer's stretch, so a looped *and* stretched cue has `* 100 / <stretch>` baked in — change the stretch by hand afterwards and the loop keeps the old rate, which the tool description says. `loopOut("cycle")` on the remap keys would survive that edit natively and is the thing to swap in if a live pass ever shows the `%` form misbehaving; it was not chosen because its last key sits at the file's end, which for audio is one frame of silence per cycle. A fade's fit is measured against the cue's *placed* length, and `__fadeFitProblem` is pure so it can run twice: at plan time wherever the length is already known (a `footageId`, a reused item, a capped `outPoint`, a loop's chosen end) and again after the imports for the files it had not seen — still before any layer exists, so a misfit names every offending cue at once and costs only the imports, which the rollback takes back. `-48` is the default `fadeFloorDb` because it is the bottom of the range AE's own Audio Levels slider offers and 1/256 of the recorded amplitude. **What no offline test can hear or see:** that AE 2026 accepts `startTime`, `thisLayer.source.duration` and `%` on a Time Remap expression and plays the bed past the file's length; the fade being audible on a RAM preview; stretch changing pitch; and which point AE holds when `stretch` is set — recipe 40.

## Motion Graphics templates

- **`exportAsMotionGraphicsTemplate` invalidates every reference held across it.** Not just the `CompItem` — `app.project` too. Measured on 26.3: after a successful export, a `comp` captured beforehand throws `Object is invalid` on `.name`, and so does an `app.project` captured beforehand, while a fresh `app.project.itemByID(id)` returns a working comp. The first version of `export_mogrt` built its result object from the pre-export `comp` and therefore threw *after* writing a perfectly good `.mogrt` — reporting a failure for work that did happen, which is the same class of lie as swallowing an error. `mogrt.jsx` captures `id` and `name` as primitives before the call and re-fetches after it. Nothing about the error says which object went stale, so if a mogrt op ever starts throwing `Object is invalid`, look for a handle held across the export before anything else.
- **`app.beginSuppressDialogs()` is what makes a scripted `.mogrt` export usable, and it was worth measuring.** Issue #23 filed it as untested. It is not: with a comp using a non-Adobe font, the export returns in ~3s suppressed and blocks past 60s unsuppressed, writing nothing until someone clicks OK on "The following 1 fonts were not synced from Adobe". `endSuppressDialogs(false)` must run in a `finally` — leaving dialogs suppressed would silence every warning for the rest of the user's session.
- **Suppression costs the only channel AE has for saying why, and that silence must never be read as a dialog.** `exportAsMotionGraphicsTemplate` answers with a bare boolean, so under `beginSuppressDialogs()` a refusal and a success-that-wrote-nothing are indistinguishable from a script. The old failure message filled that gap by naming a modal dialog — and the case that exposed it was a comp with an **empty Essential Graphics panel**, which AE simply will not export: no file, no dialog, no word of explanation. The user was sent to click something that did not exist while the real fix, adding one controller, went unmentioned (issue #71). Under suppression a blocking dialog is the one cause ruled out *by construction*, since suppressing them is precisely what the call did, so the message may not name one there; unsuppressed, it is the first thing to look at. Everything else reports as **unknown**, and the diagnostic offered is the one that actually reaches AE's own reason — the user running the same export by hand from the Essential Graphics panel, where AE shows its error in the UI. Same shape as `BridgeTimeoutError` vs `BridgeUnreachableError`: two failures, opposite remedies, no shared sentences.
- **So `export_mogrt` checks every precondition it can *before* exporting, and refuses naming it.** `motionGraphicsTemplateControllerCount === 0` is the one from #71; the project having never been saved, a name that resolves outside the destination folder (measured through `File.parent`, not a list of illegal characters — `packages/jsx/*.jsx` may not branch on platform), a blank name, a destination that refuses a write probe, and a name collision are the others. All of them run before the project is touched at all: no rename, no `app.project.save()`, no export attempt, so a refusal costs the user nothing. Two rules hold it honest: **only an explicit `0` refuses** — a controller count the host will not answer comes back `null` and exports anyway, because an unanswered question becoming a confident refusal is the same mistake pointed the other way; and the refusal message for the empty panel contains the word "dialog" nowhere at all, denials included, since naming one is what sent people looking. `tests/unit/mogrt-preconditions.mjs` covers the lot, including that `endSuppressDialogs` still runs when the export itself throws.
- **The `.mogrt` filename comes from `comp.motionGraphicsTemplateName`, not the comp name**, and it defaults to the literal `"Untitled"` for a template assembled by script. Left alone, every export in a project overwrites the same `Untitled.mogrt`. `export_mogrt` defaults it to the comp name but leaves a name the user actually set alone. Related: `CompItem.posterTime` does not exist (the thumbnail is the comp's first frame, hence the black one on anything that fades up), and there is no `getMotionGraphicsDataName` — only the reverse-indexed `setMotionGraphicsControllerName`.
- **`add_essential_property` reads the panel back instead of believing the add (issue #177).** `Property.addToMotionGraphicsTemplate(comp)` / `addToMotionGraphicsTemplateAs(comp, name)` return a boolean, and three things about them were unmeasured when the op was written: whether a false can come with a controller anyway, whether adding a property already in the panel makes a second controller, and which end of the list `getMotionGraphicsTemplateControllerName(index)` puts a new one at (the guide says index 1 is the newest; that has not been re-measured here). So the op reads `motionGraphicsTemplateControllerCount` and every controller name before and after, finds the new controller as the index whose removal leaves the old list (`__newControllerCandidates`, order-agnostic) — and when duplicate names leave more than one candidate, reports no index and never renames, since a guess can rename the user's existing controller, and treats an unchanged count as a refusal whatever the boolean said. A requested `name` that does not read back gets one `setMotionGraphicsControllerName` on the found index and a throw if it still disagrees. `canAddToMotionGraphicsTemplate(comp)` is asked first so the common refusal (a path, a mask, a group) changes nothing. All of that is offline-tested against a mock; the three questions above, whether the add is undoable inside the dispatcher's group, and whether it sets the panel's primary comp on a comp that has never had one are for a live pass.

## Comps, footage and project items

- **AE fabricates dimensions for an SVG with a very large viewBox, and the numbers depend only on the viewBox.** A synthetic file with the reported `0 0 278050 333334` imports as **15906x5654** — byte for byte the dimensions in issue #33, from an entirely different SVG. It will not even rasterize: `saveFrameToPng` on a comp containing one produces no file at all, where a healthy SVG renders in seconds. That reproducibility is what makes the aspect-ratio check in `footage.jsx` a reliable detector rather than a heuristic.
- **`CompItem.duplicate()` is shallow, and the copy looks finished.** The
  duplicate's precomp layers point at the *same* nested comps as the original,
  so "make a variant of this rig" and then editing the variant edits the
  original too — silently, and usually noticed several scenes later.
  `duplicate_comp` keeps that as the default because it is AE's own Duplicate
  and changing it would surprise anyone who knows the app, but it says so in the
  result rather than leaving it to be discovered, and `deep:true` duplicates the
  nested comps and re-points the copy at them. Two things `deep` has to get
  right and a hand-rolled `run_jsx` version usually does not: the same nested
  comp appears on several layers, so it is duplicated once and reused (keyed by
  the *original* id) rather than fanned out per reference; and the copy is
  registered in that map *before* the walk descends into it, which is what makes
  a cycle terminate. A nested duplication that fails part-way names every comp
  it created in the error — the objects are real and nothing rolled them back.
- **A comp checkpoint restores into the original comp, because a swap changes the comp's id.** `revert_comp` copies the checkpoint's layers back with `copyToComp`, re-parents them with `setParentWithJump` (the copy keeps parent-relative values and loses the parent; plain `parent =` would compensate them away), re-applies track mattes and locks, and only then removes the old layers — so a failed copy leaves the comp untouched. Effect layer picks (Layer Control, Displacement Map, Set Matte) and text-path mask picks are by index, so they are set from the checkpoint only after the old layers are gone, when the indices match. The comp id, name and every usage survive; every layer id changes and is mapped in `layerIdMap`. Measured on 26.5 (live pass, 2026-10-29): `duplicate()` copies the item comment; the in-group refusal is a throw, not a dialog; `copyToComp` renames an explicitly named layer `<name> 2` on a collision and bakes a parented layer's keys into comp space when the destination holds the parent's namesake — so the op copies with the parent detached and renames afterwards; a copied matte fill arrives with `trackMatteLayer` null; `itemByID` of a deleted id throws, so lookups go through `__findItem`; a 300-layer revert took 2.2 s. Originally inferred and listed for recipes 47–50: whether `duplicate()` carries the item comment (the tag) across, whether `copyToComp`'s undo-group refusal is always a throw and never a dialog, what a copied 2023+ track matte points at, what happens to Essential Graphics entries on replaced layers, what a copied Layer Control pick resolves to before it is re-pointed, whether `copyToComp` trims a layer to a shorter destination, and how long a ~300-layer revert takes against the bridge timeout (recipes 51–55). The reasoning is in [subsystems.md](subsystems.md), "Comp checkpoints".
- **A solid's footage item outlives every layer that used it, and `delete_comp` used to leave all of them behind.** `layers.addSolid()` makes two things: a `FootageItem` whose `mainSource` is a `SolidSource`, filed in the project's Solids folder, and a layer pointing at it. Removing the comp — or the layer — removes only the layer. Nothing warns, and once orphaned the item is indistinguishable in the Project panel from a solid still in use unless something reads `usedIn`. A verification pass that built and discarded test comps left **1,863** of them to sweep out by name (issue #83). Two things fix it, and the scoping of the first is the whole point. `delete_comp({purgeUnusedSolids:true})` collects the solid items from the deleted comp's **own layers** before the removal and afterwards removes only those whose `usedIn` is empty — deleting comp A must never reach a solid that only some other comp uses, and an unused solid that was never A's is someone else's work in progress, not this call's to judge; a shared one is kept and reported with the comps keeping it. It is off by default because a solid can legitimately be shared, and the default result counts what it left (`unusedSolidsLeft`) so the orphan is visible at the moment it is made. `purge_unused_footage` is the project-wide sweep — AE's own Remove Unused Footage with a `dryRun` and a report — and it decides by two tests, both `instanceof`: `FootageItem` (a `CompItem` is also an AVItem with a `usedIn` of its own, and a nested comp nothing uses any more is exactly what a naive sweep deletes) and, by default, `SolidSource` on `mainSource`. Both ops collect in one pass and remove in a second, highest project index first, and both stop at the first `remove()` that throws and name it, what went before it and what was never attempted, because nothing rolls back. The dry run lists in the order the real run removes, so the plan is the truth about order too. `tests/unit/purge-footage.mjs` holds all of it; what it cannot hold is whether `usedIn` already reads empty in the same `evalScript` as the `comp.remove()` — recipe 35 is that measurement, and on 26.3 it does (measured 2026-09-08).

## Layers and transforms

- **`Property.canSetValue` does not exist in AE 26.5 — it reads `undefined` — and a hidden property says so through `canSetExpression:false` instead** (measured 2026-10-30 on 26.5, PR #204). Cameras and lights carry transform properties that resolve by match name but are hidden: Scale on a camera, Point of Interest (`ADBE Anchor Point`) on a one-node camera, Orientation on a point light. Writing one throws `Can not "set value" with this property, because the property or a parent property is hidden.` — after any earlier field in the same call has already landed. `set_transform` therefore resolves every field first and refuses on `canSetExpression === false` before the first write; if a write still throws, the error names the fields already written in that call rather than claiming nothing changed.
- **AE's scripting DOM has no `toComp`/`toWorld`.** Those exist only in the expression language, so anything needing a world transform reimplements the matrix chain — `layers.jsx` does, for `parent_layer`'s `preserveTransform`. Two things follow: 2D only (AE's 3D rotation order is not worth guessing at), and a child's `Position` has two possible readings of its parent's space that differ by the parent's anchor point, so the position correction only fires when AE's own answer matches *neither* — the one case where AE is provably wrong.
- **Track mattes, measured on 26.5 (PR #205, issue #149).** `layer.setTrackMatte(matte, type)` takes a matte anywhere in the stack, including below the art, and `trackMatteLayer` / `trackMatteType` read back as set; the matte layer's video goes off. A type change on a layer that already has a matte is `setTrackMatte(current, newType)`, and keeps the layer. Two calls do less than their names say: **`removeTrackMatte()` clears the matte layer but leaves `trackMatteType` as it was** (ALPHA, say), so `set_layer` follows it with `trackMatteType = NO_TRACK_MATTE`, which clears the type; and **assigning `trackMatteType` to a layer with no matte layer reports success and sets no matte** (seen on layer 1, where there is no layer above to fall back on), so `set_layer` refuses a type without `layerId` on a layer with no matte rather than pass that silence on. Every name in `BLENDING_MODES` exists in `BlendingMode` on 26.5, including Adobe's `SILHOUETE_ALPHA`; the Line Cap, Line Join and Fill Rule popups take 1–3, 1–3 and 1–2 in the order the schema names them. `tests/unit/layer-enum-names.mjs` holds the mock of all of this.

## The render queue

- **`OutputModule.setSettings` rejects Format, Channels, Depth and Color as read-only**, although `getSettings(GetSettingsFormat.SPEC)` lists all four — SPEC is the domain, `STRING_SETTABLE` is the writable list (issue #95, measured on 26.3 from four starting states). So `add_to_render_queue` takes output-module and render-settings **template names** and nothing else, refuses an unknown name with the list that exists, and reads `getSettings(STRING)` back into the result — the template name is a promise and the read-back is the fact. A refusal after the item was added removes it again, because #95 also found the leak: a throw mid-setup left a temp item in the user's queue.
- **`app.project.renderQueue.render()` is not how `render_queue` renders, and never should be** (issue #137). It is synchronous: it holds the ExtendScript thread, and AE's interface with it, for the whole render. Three consequences, each disqualifying on its own. Every later `evalScript` waits behind it on the panel's mutex, so the session is dead for the duration. The server's op timeout fires on a render that is still going, and the timeout's own remedy ("do not re-send, it may still be running") would be correct and useless. And nothing can stop it — no script call cancels a render in progress; the Stop button is the user's. *Not measured here; Adobe documents `render()` as blocking and the issue asked for this to be designed around rather than discovered.*
- **Nor Media Encoder (`queueInAME`).** It needs AME installed, renders with AME's own presets instead of the output-module templates #95 says to rely on, and tells a script neither progress nor completion — so "verify the output exists" would be polling a folder for a file of unknown name, and cancel would have no handle at all.
- **`aerender`, spawned by the server, is the route.** It renders one render queue item exactly as configured (`-rqindex`), prints one `PROGRESS:` line per frame, exits with a status, and is a process that can be killed. Its costs, all surfaced to the agent: it renders the **saved file**, so unsaved changes are refused unless the caller passes `saveProject:true` (the save is never a surprise; a clean project is not saved at all, except — again only with `saveProject:true` — to record footage paths that moved, below). The save runs under `beginSuppressDialogs` like `export_mogrt`'s, and since a suppressed save of a read-only, locked or converted project simply does not happen, it is checked afterwards by AE's own `dirty` flag — still dirty is refused. Not by the file's modified time: `File.modified` has one-second resolution, and the live run (26.5) refused a save that had happened because it landed in the same second as the previous one. Each job renders a **private copy** of the .aep made while the lease is held: aerender reopens the project once per item, and a Cmd-S or an `export_mogrt` between items would otherwise change what later items render and move their `-rqindex`. The copy lives in the **OS temp folder**, under a chain of one-letter folders as deep as the project's own folder (`<tmp>/ae-mcp-render/<jobId>/a/a/a/a/a/show.aep` for `/Users/me/work/show/show.aep`; why, under "Where outputs land" below), not beside the project. A sibling was tried first and rejected in review: a dot prefix hides nothing on Windows, and project folders are routinely Dropbox/iCloud/OneDrive folders that would upload a full .aep copy on every render. The cost is footage AE can find only through its *relative* path. AE stores an absolute and a relative path per file and tries the absolute one first, and a project render_queue just saved — or one saved since it was last moved — carries current absolute paths, so the copy resolves them wherever it sits. What is left is a project that was moved and not re-saved — and that is now refused before anything renders, in any language — see "Footage the copy cannot find" below (issue #145). aerender's own missing-footage line remains the second layer: it may report missing footage and still **exit 0**, writing AE's placeholder into a fresh, non-empty file the on-disk check would accept — so any output line `isMissingFootageLine` recognises, or any line where AE says it logged errors (`loggedErrorCount`), fails the item regardless of the exit code. Failing on *any* logged error is a deliberate choice over narrowing to known-fatal classes: the only measured case (below) was a corrupt file, nobody has a list of which AE render errors leave a usable one, and reporting a broken file as done is the one outcome this repo refuses. What it costs is a false failure on a harmless error, so the failure quotes aerender's matched lines and says the file was left in place — the agent can show the user both and let them judge. **Measured on 26.5** (English), verbatim, exit 0, corrupt file: `WARNING:After Effects warning: logged 9 errors, please check log.  First error was “error: Unable to Render: File Not Found /…/pic.png”`. The words are inside the curly quotes; the first matcher stripped every quoted span (to stop a comp named "Cannot Find Me" from matching) and passed this line. Quoted spans are now dropped unless they begin `error:` — AE quoting its own message — and paths are dropped either way. The line is a test fixture. A hard-killed server leaves its snapshot folder behind and Windows never empties %TEMP%, so each new render removes `ae-mcp-render/<job>` folders more than a day old (`sweepStaleSnapshots`) — never newer ones, which another session may be rendering from, and never its own. The rule that AE resolves absolute paths first comes from Adobe's documentation and has not been measured here — recipe 67. Whether aerender adds the copy to AE's recent-projects list is recipe 68. Edits made during the render are not in it; it is a whole headless After Effects, so renders run one at a time; and the live Render Queue panel never learns the item rendered — so when the job ends — completed, failed or cancelled — the server unticks the Render box of every item it verified (`_render_mark_done`, matched by comp and output path, never by index alone), or the next `render_queue` would render them again. That is a project change, so it is one named undo step, "AE MCP: mark rendered", opened and closed by `dispatch()` inside the one call. It is one step for the whole job rather than one per item on purpose: per-item steps would land in the user's undo history every few minutes, between their own edits, while one step at the end is a single entry they can read and are told about. An item verified before a failure or cancel is still unticked, because its file is good. Rendering items the agent did not add needs an explicit `all:true`, and an existing output — which an item queued by hand never had checked — needs `overwrite:true`. The write lease covers only the prepare and the save, not the render — see "Render" under "Special return shapes" in [architecture.md](architecture.md).
- **Why the server spawns it and not the panel**, although the panel has Node too. The panel does not update itself (see [subsystems.md](subsystems.md)): a wrong aerender path or a kill that misses the render engine, shipped in the panel, would stay wrong until the user reinstalled and relaunched AE. In the server it is fixed by an npm update, it sits beside the other host differences in `setup/platform.ts`, it is testable against a fake aerender (`tests/unit/render-queue.mjs`), and cancel is a local kill rather than a bridge round trip to a panel that might be busy. Both processes are on one machine by construction — the bridge listens on 127.0.0.1 only.
- **An exit code is not a render.** Measured on 26.5: 1 render in 8 with missing footage came back `completed` — a 1 MiB file, no frame lines, and none of aerender's output past "Launching After Effects". Four rules now hold together. **Missing footage is refused before anything renders**, language-independently: `_render_prepare` walks each item's comp and its nested comps and asks every FootageItem `footageMissing`, naming the missing items; aerender's wording is only the second layer. AE reported a file deleted while the project was open as present until the project was reopened (26.5), so `footageMissing` misses that case; the line detection caught it then, and the server now catches it first, in any language, by checking every footage path the plan lists on disk (`checkPlanFootage`'s `gone`, issue #145). Only footage the render *reads* is refused (issue #144) — see "Which footage a render reads" below. **Frame counts** are never reported lower than the file proves (`verifiedFrameCount`: fresh frame files, or movie duration × the span's frame rate) — on 6 of 14 good live renders the progress lines read were 26–29 of 30. The item is decided only after stdout and stderr have *closed* (`close`, never `exit`); after `exit` the wait continues while a render process for the job is alive, because an engine that inherited the pipe may still print the warning — capped at 60s, after which the engine is killed with the same name-and-path matcher cancel uses and the item is decided on what was read. **The file is judged**, and how depends on whether frame lines were read: with lines, a sequence needs as many fresh frame files as frames reported and a QuickTime/MP4 must be a complete ISO media file (boxes tile it, `moov` present — the corrupt live file had media and no index) whose `mvhd` duration matches the span within a frame. Without readable lines — an AE in another language, or output that never arrived — a sequence needs as many files as the span has frames and a QuickTime/MP4 needs `moov` and the matching duration; any other format cannot be judged from its bytes and fails, saying so. So a non-English AE renders QuickTime/MP4 and sequences fine and fails only on formats nothing here can inspect. A finished item is accepted only when every output file exists, is non-empty and has an mtime at or after the item started (2s slack for coarse filesystems); an image sequence needs at least one matching frame file that new. A path that already held a previous render (`overwrite:true`) is exactly the case where "the file exists" would lie.
- **Which footage a render reads (issue #144).** The first up-front check refused any missing footage anywhere in the comp tree, including footage on switched-off layers and on layers outside the rendered span — safe, and it blocked legitimate renders (a disabled reference plate, an alternate take parked at the end of the timeline). `__rqFootageUse` in `render.jsx` now decides per layer, and the rule is chosen so that every doubt resolves towards *read*: reading too much costs the refusal #144 is about, reading too little renders the placeholder and calls it done. A layer's footage is read when the layer is switched on — video, or audio with `hasAudio` — and its in/out overlaps the span **padded by one frame** (motion blur and frame blending reach a frame out). It is read *regardless* of both when the layer is a track matte (`isTrackMatte`, the layer named by any layer's `trackMatteLayer`, and — the pre-23 rule — the layer directly above any layer with a `trackMatteType`), or when any layer in the same comp points at it through a **layer-valued property** (`PropertyValueType.LAYER_INDEX`) in its effects or light options: Displacement Map, Set Matte, Compound Blur, Card Wipe, a Layer Control, a light's source. Those pull pixels from layers that are switched off — that is how they are normally used. A layer-valued property whose value AE will not give, or one driven by an expression, makes every layer in that comp count as read. **A parent is not a read**: parenting takes the transform, never the pixels, and a missing file keeps its dimensions. Nested comps are walked with the span mapped into their own time through `startTime` and `stretch` (`(t − startTime) × 100 / stretch`), and given *all* of their time when the precomp layer has time remapping, **any effect** (Echo, Time Displacement, Posterize Time and Timewarp read other times, and listing the time effects would be a list to fall behind), or a stretch AE will not report. **Time effects on other layers reach back too** (review of #146): Echo, Posterize Time or Timewarp on an *adjustment layer* reads the composite of every layer below it at earlier frames, so a layer that ended before the span still reaches the render. So any comp where a switched-on layer carries an effect whose match name or display name looks like a time effect (`TIME_EFFECT` in `render.jsx`, matched loosely on purpose: a false match costs a skip) is read over its whole duration. A name list cannot know third-party effects (Twixtor, RSMB), so on an *adjustment* layer the rule is inverted: every effect counts as time-reading unless its match name is on `NON_TIME_EFFECTS`, a short list of stock current-frame effects (Curves, Lumetri, Levels, blurs and so on; the match names are not measured here, and a wrong one costs only a refusal). On any other layer an effect reads only that layer's own source, which the in/out check already covers. A switched-off precomp's contents are walked too, so its missing footage is reported as skipped rather than vanishing; a comp reached both ways is read. Solo switches and guide layers are not used to skip anything: whether they apply depends on the render settings template. **The one doubt the walk cannot resolve is an expression**: `sampleImage()` reads any layer's pixels by name, and names in code are not something to guess at. So when *any* expression in the walked comps calls `sampleImage`, every skip becomes a warning instead (`footageWarnings` on the render_queue result and on each rendered item) — rendered, not refused, as the issue asked, and never silent. That scan walks every property of every layer. It runs whenever anything was left unread, missing or present: present footage on a skipped layer is added to the on-disk check (#145) when an expression may sample it. It is skipped only when nothing was skipped, where its answer could change nothing. Not covered: an expression reading `comp("Other").layer(…).sampleImage()` reaches a comp the walk never visits; a proxy's file is not checked. Whether aerender itself complains about missing footage on a switched-off layer — which would fail the job through the second layer — is [recipe 69](verification-recipes.md). `tests/unit/render-footage.mjs` holds each rule against a mock DOM.
- **Footage the copy cannot find (issue #145).** The render reads a copy of the .aep in the temp folder. AE resolves a footage file by its stored absolute path first and then by its path relative to the project — and relative to a copy in the temp folder that path leads nowhere. When the user's AE found a file only through the relative path (the project folder was moved and not saved since), the copy renders the missing-footage placeholder, and only aerender's English wording ever said so. Three routes were weighed. **Learning aerender's localized wording** was rejected first: the core invariant is that a placeholder render never reports success in any language, and a list of translations is a list to fall behind. **Rendering from a copy beside the original** in that case only would reproduce the GUI's resolution exactly, but it brings back the cloud-sync upload that put the copy in the temp folder, puts a stray .aep in the user's folder for the length of the render, and breaks the engine lookup, which identifies a job's processes by the `ae-mcp-render/<jobId>/` tail of the snapshot path. And it still renders on a resolution nobody checked. **Detecting it and saving** was chosen. A save makes After Effects write the absolute path it resolved, and the result is checkable before anything renders. Detection needs the *stored* path, which no scripting API exposes, because `FootageItem.file` is the resolved one. So the server reads the saved .aep itself: **measured on 26.x macOS files**, each footage item holds a LIST `Als2` whose `alas` chunk is UTF-8 JSON, `{"ascendcount_base":1,"ascendcount_target":3,"fullpath":"/…/pop.wav","platform":2,…,"target_is_folder":false}`. The ascend counts are the relative path; `fullpath` is the absolute one. `storedFootagePaths` scans the bytes for those chunks and does not parse the format; `.aepx` is read from `fullpath="…"` attributes, which is *assumed and unmeasured*. `_render_prepare` lists every file the render reads (the #144 walk), and `checkPlanFootage` sorts each into one of three outcomes. **Gone**: the resolved file is not on disk. That is the 26.5 deleted-while-open case, refused outright, since no save can bring it back. **Stale**: the file is on disk, but no recorded absolute path leads to it. Paths are compared after NFC normalization; on Windows also without case or slash direction; through `realpath`, so `/tmp` and `/private/tmp` or a symlinked volume are one file; and a folder record covers what is inside it. **Unreadable**: the render reads footage and the file yields no path records at all. This one **fails open, deliberately** (review of #146): an unreadable file is a project format this does not know — an older project, an .aepx, a future AE — not evidence of moved footage, and refusing it would refuse every render with footage from such a project. The render goes ahead on what held before #145 (`footageMissing`, the on-disk check, aerender's missing-footage and logged-error lines, the judging of the file) and the result carries `footagePathsUnchecked` saying so. What that leaves open is one stacked case: a project moved and not saved, in an unreadable format, on a non-English AE, writing a format the file judge cannot inspect. **Order matters** (`saveAndCheckFootage`, review of #146): the saved-path check reads the .aep on disk, so on a project with unsaved changes it runs only *after* the save — the old file does not record footage imported since, and the first version called a new project's freshly imported footage "moved since saved", or the never-saved-with-footage file unreadable. Unsaved changes without `saveProject` get the unsaved-changes refusal first; footage gone from disk is refused before any save; a clean project's file is checked before. The file is read in 16 MB chunks with an overlap longer than any record, so an .aep with embedded media over 2 GB is read rather than mistaken for unreadable. Stale is refused naming the files unless `saveProject:true` — the same consent rule as unsaved changes. With it, `_render_save({force:true})` saves even a clean project. A clean project's `dirty` flag cannot show whether a suppressed save happened, so the saved file is **read again**, and any path still stale is refused with "The project WAS saved, but nothing was rendered". All of it is Node reading a file, so none of it depends on aerender's language. *Unmeasured:* UNC paths against mapped drive letters on Windows (`\\server\share\…` stored, `Z:\…` resolved, or the reverse, compare as different and are refused as stale after the save); a folder record that is very broad (a `/Volumes/X` folder would cover everything under it); older-format projects (fail open, above); proxies (a proxy's file is not checked at all); and the Windows form of `fullpath` (if AE writes something the canonical form does not match, every Windows render with footage is refused as stale even after the save — failing closed, and the first thing [recipe 70](verification-recipes.md) checks), and whether an image sequence records its first frame or its folder (both are handled). `tests/unit/render-footage.mjs` builds `alas` chunks the measured way.
- **Where outputs land: the copy sits under a chain of one-letter folders (issue #215).** **Measured on 26.5 (macOS):** the saved project stores each output module's folder as an alias, `fullpath` plus ascend counts (the relative path, as for footage above), plus the file name. aerender uses the **relative** form whenever the folder it names exists next to the project it was given, and the absolute one otherwise. With the copy at `<tmp>/ae-mcp-render/<jobId>/<name>.aep`, an output **beside the project** resolved to the job folder itself. It was written there and deleted with the copy, and the job failed honestly with "output cannot be verified: …/out.mp4 does not exist". An output **one folder up** resolved to `<tmp>/ae-mcp-render/` and was written there as `out4.mp4`, outside any job folder, so nothing ever removed it. An output in `/private/tmp`, or in a subfolder of the project's folder that did not exist beside the copy, rendered correctly: the relative form named a folder that did not exist.

  **Four fixes were weighed.**
  - **`aerender -output <path>`** was rejected. aerender's usage applies `-output` to the item it renders, but it names one file: it cannot address an item's second output module. An item with several output modules is how this queue is meant to be used (#95). Its interaction with `-rqindex`, with a template whose format changes the extension, and with an `[####]` sequence name is unmeasured. It would also replace the path the user set in the Render Queue panel with one this server re-derived, which is a second source of truth for the same fact.
  - **Rewriting the output paths in the copy** (`outputModule.file = new File(absPath)` before the save) changes nothing. After Effects stores an alias with ascend counts whatever the script assigned, and the copy cannot be opened in AE without closing the user's project.
  - **Editing the alias bytes in the copy** (the `alas` JSON) would work only if After Effects honoured an edited record, which nobody has measured.
  - **Placing the copy so the relative form is harmless** was chosen.

  **How the chosen fix works.**
  - **The chain.** The copy goes at `<tmp>/ae-mcp-render/<jobId>/a/a/…/a/<name>.aep` (`snapshotLayout`). The chain is as deep as the **deeper** of the project folder's two spellings, the path AE reported and its `realpath`, plus two spare levels (`SPARE_LEVELS`). Which spelling AE counts its ascend counts against is not measured, and `~/Dropbox` → `~/Library/CloudStorage/Dropbox` differs in depth, so the chain covers both. Every folder the ascend counts can climb to is then one of the job's own.
  - **Why one letter.** Only the depth matters to the relative form, not the names. One letter also keeps the path short on Windows: a first version mirrored the real folder names, which doubled the path's length against `MAX_PATH`. The letter is the first of `a`–`z`, `0`–`9` that is no folder or file name, in any case, of the project's or any output's path in either spelling.
  - **Outputs elsewhere.** If the output's folder is **not** the project's folder or an ancestor of it, the relative form continues below the climb with a real folder name, which never matches the letter. So it names nothing, and aerender uses the absolute path. A subfolder of the project, a sibling branch, another volume and `/private/tmp` all behave this way.
  - **Outputs beside or above the project.** If the output's folder is the project's folder **or an ancestor of it**, aerender writes into a chain folder. After **every** aerender exit, `relocateShadowOutputs` scans the **whole** job folder, not only the predicted level (`shadowDirs`). A file goes to the output whose file name it has, or whose `[####]` pattern it matches; when two outputs share a name, it goes to the one whose predicted level it is at. The move is a rename, or a copy then unlink across volumes. Then the file is verified as usual.
  - **Order matters.** Relocation runs before any verdict, so a failure that says "the file was left in place" is true. It also runs before a cancel's report, and again in `cancel()` for what an engine wrote after aerender exited, so the cancel's `partialFiles` names the partial file at the asked path rather than letting it be deleted with the copy. It runs on the exit/signal path too.
  - **A cancel owns the job folder until it has reported.** Live on 26.5, aerender exited on the cancel at once while its engine was still being stopped, and `run()` removed the job folder on aerender's exit — so a partial the engine wrote after that was deleted, and `partialFiles` came back empty. `run()` now waits for `cancel()` to finish (`Running.cancelDone`) before the folder goes.
  - **A cancel never names or replaces a file that was there before the render.** With `overwrite:true` the asked path can hold a complete earlier render; the first version listed it in `partialFiles` (an agent told to delete partials would delete good work), and relocation would have moved the partial over it. Each item's output files are stamped (inode, size, mtime) before it renders (`stampOutputs`); `cancelledPartials` counts only files that are new or changed, and a cancelled relocation that would land on an unchanged earlier file leaves the partial in the job folder, named at that temp path, and keeps the folder (minus the copy) for the stale sweep of the first render started a day or more later. Every file is named exactly, a sequence's frames one by one and never by its `[####]` pattern: a pattern also covers earlier frames left as they were, and an agent deleting by it would destroy them. A cancel that arrives after the job is settled (the last item verified, the queue being unticked) reports nothing to cancel rather than calling a verified output partial. So does one that arrives once aerender has exited 0 on the current item, while its output is still draining (`CLOSE_WAIT_MS`, the drain cap): that item is finished, not interrupted. The cancel returns at once with `status:"finishing"` and a progress message rather than holding the caller through the drain (up to a minute); the item is reported as rendered (or failed), no later item starts, and `run()` settles the job as cancelled with the same engine check as `cancel()` (`settleCancelled`), so `stopped` means the same thing from either side. The keep rule is not only a cancel's: until an item is verified, relocation never moves its output over an unchanged earlier file. The item is verified where its file actually is, and only then moved over the earlier file (`promoteKept`), each kept file by the full path it belongs at — never by file name, since two outputs may share one in different folders; a failed item's file stays in the temp folder and the failure names it there. An output aerender writes straight to its absolute path still overwrites in place as it renders — that file *is* changed, and is reported as partial, truthfully.
  - **Failures.** A move that fails fails the job, naming both paths (or is named in the cancel note). A verification failure also names any file still in the job folder (`strayFiles`). A file that no output claims is left there and reported, never silently deleted.

  **What this guarantees, and what it does not.** Within the depth the chain covers, both spellings plus two levels, nothing aerender resolves relatively can land outside the job folder. A third spelling deeper than both by more than two levels could still climb out to `ae-mcp-render/` or `<tmp>`. No such case is known, and it would fail verification as "does not exist" rather than report success.
  - **Cleanup.** The outputs the old layout leaked into `ae-mcp-render/` are plain files there. `sweepStaleSnapshots` now removes them once they are a day old, like old job folders.
  - **The job folder is derived.** `removeSnapshot` and `touchSnapshot` take `jobFolder(tmpRoot, jobId)` and never search for it. The engine lookup (`snapshotMarker`) takes the command line from the last `ae-mcp-render` segment on. That segment is unambiguous, because below it come only the job id, the chosen letters and the file name, never a folder name of the user's.

  **Unmeasured.**
  - The Windows form of the alias, and whether aerender resolves relative-first there too. The fix holds either way: an absolute resolution never touches the chain.
  - Whether a long `%TEMP%` plus the project's depth (two characters a level) passes `MAX_PATH` for aerender.exe.
  - Which spelling AE counts against. Both are covered.

  Confirm with [recipe 72](verification-recipes.md). `tests/unit/render-queue.mjs` drives a fake aerender that resolves outputs the measured way: outputs beside, above, below and on a sibling branch, plus a sequence. It also covers a project reached through a symlink of another depth, counted either way, and a cancelled render's partial output — including one the engine writes after aerender has exited, and a cancel over a complete earlier render.
- **Cancel stops aerender AND its engine, and says `stopped` only once neither is left.** The first design assumed the engine stays in aerender's process group. **Measured on 26.5 (macOS), it does not**: aerender starts `…/aerendercore.app/Contents/MacOS/aerendercore -noui -project <snapshot> -rqindex N … -aerenderpid <pid>` with PPID 1 and a process group of its own, so the group signal stopped aerender while aerendercore kept rendering at 1–3 GB; it ignored SIGTERM for 8s. So the engine is found by its command line (`findRenderProcesses`, `ps -axww -o pid=,args=`), and a process counts as this job's only when **both** its executable is named `aerender`/`aerendercore` **and** its arguments contain this job's snapshot path (everything from `ae-mcp-render/<jobId>/` on, letter chain included, so `/var` vs `/private/var` still matches and two jobs on one project stay apart). A first version matched the job id alone; review showed it would kill any shell or agent command that mentioned the id, and on Windows the PowerShell search itself, whose pid has usually exited — and may have been reused — by the time `taskkill /T` ran. So: the searcher's own pid is excluded, each pid is re-checked by name and arguments immediately before it is signalled, and only that one pid is signalled, never a tree. `tests/unit/render-queue.mjs` holds the decoys (a shell line with the id and path, a non-aerender process holding the path, another job's aerender). Both get SIGTERM, anything alive after the grace period gets SIGKILL, and `stopped` is true only when aerender has exited and the lookup finds no live process for the job. Every job end — completed, failed, cancelled — reaps any engine still carrying its id, and the exit/signal handlers do the same synchronously. Windows: `taskkill /T /F` for aerender's own tree (the child this server spawned and still holds), plus the same name-and-path lookup through PowerShell's `Win32_Process` in case the engine is detached there too — *unverified on Windows*, including the engine's name: if it is not `aerender*.exe` there, only the tree kill reaches it ([recipe 60](verification-recipes.md)). So is where aerender lives: candidates come from the running AE's `Folder.appPackage` (beside the `.app` on macOS, inside `Support Files` on Windows) and the stock install folders, overridable with `AE_MCP_AERENDER` — [recipe 58](verification-recipes.md).

- **`set_house_style` writes through ExtendScript's `File`, whose macOS default `lineFeed` is `"Macintosh"` — every `\n` became a bare `\r` on disk.** The round trip hid it (`File.read` normalises line endings), the unit tests never touch a real `File`, and the only symptom was a designer's editor showing the guide as one line. `style.jsx` sets `file.lineFeed = "Unix"` before opening for write; anything else in `packages/jsx/` that ever writes a text file must do the same, since nothing offline can catch it — recipe 10 reads the bytes.
